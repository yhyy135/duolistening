# duolistening

A listening-practice tool. Import a podcast episode, transcribe it with your own LLM keys, and study it through a lyrics-style transcript: the current line scrolls into view and highlights as it plays, your native-language translation sits under each line, and Japanese gets furigana and part-of-speech colouring.

Read [CONTEXT.md](CONTEXT.md) for the domain vocabulary (**Resource**, **Transcript**, **Line**, **Word**, **Token**, **Suggestion**, **Library**) and use those words. Read [docs/adr/](docs/adr/) for why the architecture is shaped the way it is — seventeen decisions, a few paragraphs each. 0008–0011 rebuilt it: they supersede 0001, 0003 and 0007 outright, and 0011 supersedes the part of 0005 that says when Tokens are computed. 0012–0014 are what the browser half grew afterwards — an import that does not need an API key, where the recommendations come from, and why the manifest exists — and they supersede nothing. 0015 takes Tokens out of annotation altogether and hands them to the player, superseding 0011's answer to that same question: kuromoji is local, so Tokens wait for no request and need no key. 0016 and 0017 are the interface's: one DOM drawn in two looks, and covers loaded straight from their host.

**Everything lives in the reader's browser.** No server, no accounts, no database, no `data/` directory. Settings — API keys included — the shelf, Transcripts and audio blobs are all in IndexedDB, which is what lets several people share one deployment while each pays for their own transcription (ADR 0008). The only thing deployed beside the static page is a Cloudflare Worker that proxies bytes (ADR 0009).

## Commands

```bash
npm test          # node:test, no framework
npm run typecheck # tsc --noEmit
npm run format    # prettier
npm run build     # assets + vite → dist/web
npm run dev:web   # assets + vite on :5173
```

`assets` runs automatically before both `build` and `dev:web`. It writes what has to be served from the app's own origin: the Settings check's probe clip, kuromoji's dictionary and bundle, and the home-screen icons. Its output is gitignored — `manifest.webmanifest` and `sw.js` sit in the same directory and are not, because they are text a reviewer can read.

There are no external binaries. ffmpeg and yt-dlp went with the server.

**Every commit moves the version.** `package.json`'s `version` is the only place the
number lives: `vite.config.ts` reads it into `__VERSION__` and the Settings screen
prints it bottom right, which is where a bug report quotes it from. Semver, read off
the change the commit makes — a fix is a patch, a feature is a minor, and a major is
an incompatible change to something already in a reader's browser: the shape of a
stored Resource or Transcript, the backup document, or the settings transfer string.
Edit the field by hand and let it ride in the same commit as the work; `npm version`
would make a commit and a tag of its own, and a number that lands separately stops
answering which build someone is running.

**Deploying** is two independent halves that know nothing about each other: `dist/web` on any static host, and `worker/` on Cloudflare. A reader points the page at a proxy from the Settings screen, so the page carries no configuration at all.

**One deployment requirement**: whatever serves `dist/web` must not send `Content-Encoding: gzip` for `/kuromoji/dict/*`. Those files are gzip _content_ which kuromoji gunzips itself, not a transfer encoding — see the invariant below, which cost an hour.

Node 22.18+ (unflagged type stripping).

## How the code is laid out

```
src/shared/  the model and the pure logic — model.ts, locate.ts, i18n.ts
src/web/     everything else: the pipeline and the three screens
worker/      the byte proxy, deployed separately
scripts/     what has to be generated into src/web/public before a build
docs/adr/    why things are the way they are
```

There is no `ports.ts` any more. It existed to hold the seams a server needed; with one implementation of everything, each module declares the narrow shape it actually depends on — the Annotator asks for `completeJson`, not for a whole TextModel.

## Invariants that are easy to break

Every one of these was a real bug. If you change the code near one, keep the test that guards it.

- **Audio is stored with its true content type, never an assumed one.** These files are MP3 — podcast enclosures nearly always are — while a pipeline naming them `.m4a` will tell `<audio>` they are AAC-in-MP4. Chrome sniffs content and hides it completely; Safari believes the label and refuses with `MEDIA_ERR_SRC_NOT_SUPPORTED`, except where an `ID3` header is magic enough to override it, so whether an episode plays comes down to coincidence. The magic bytes therefore beat the declaration, at one choke point. (`store.ts`)
- **Whatever serves the kuromoji dictionary must not claim `Content-Encoding: gzip`.** The browser would decode it first, and kuromoji's unguarded gunzip then throws inside an XHR `onload` handler — where the exception eats the callback and the tokenizer hangs with no error anywhere. (`vite.config.ts` for dev; a deployment requirement in production)
- **kuromoji is loaded as a classic script, not imported.** Its gunzip dependency ends in `}).call(this)` and keeps the result as its global, which is `window` in a classic script and `undefined` in an ES module. (`japanese.ts`)
- **The two model slots are optional, and the proxy is not.** Downloading an episode needs the proxy; turning it into Lines needs somebody's API key, and those are separate decisions. So `buildImportDeps` omits `transcribe` entirely when that slot is empty rather than handing over a client that fails on its first call, and the import reads the absence as "keep the audio and stop" — `untranscribed`, a resting state that plays and that a Resume can still finish. The player does the same with the Text Model: no annotator is built, so a Transcript shows its Lines untranslated instead of a failed request beside every one of them. What it still shows is furigana and part-of-speech colouring, because those come from kuromoji and kuromoji is local (ADR 0015) — an empty Settings screen is not a reason to study Japanese without readings. (`shared/model.ts`'s `slotConfigured`, `pipeline.ts`, `import.ts`, `player.tsx`)
- **Whether an episode plays is `hasAudio`, never the phase.** `failed` says an import stopped, not where it stopped, and the common failure now is a download that worked followed by a transcription that did not — which leaves a perfectly playable episode. Reading the phase instead had the shelf refuse to open bytes it already held. The flag is set the moment the audio is in the store, including on the resume path, so a Resource from before it existed heals the next time it is retried. (`import.ts`, `library.tsx`)
- **A retry resumes; it never restarts.** A stored Transcript means there is nothing left to do; stored audio means skip the download. Restarting would pay the transcription bill again to recover from a failed download, making the cheapest failure the most expensive. (`import.ts`)
- **One episode is imported once at a time, and `import.ts` is the only thing that knows which.** The store cannot answer it — two runs both read it before either has a Transcript to write — and the phase cannot either, since a Resource reads `transcribing` whether something is driving it or whether a reload walked away from it. The shelf used to answer it from a Set inside its own component, which the player's Retry transcription never joined: start a transcription in the player, press Back, and the shelf offered a Resume beside it that billed the same episode again. Measured before the fix — two POSTs to `/audio/transcriptions` for one episode, both in flight at once. `run` registers the id, refuses one already registered and releases it in a `finally`; both screens read `isImporting` so the button that would only error is not offered. The ceiling is one page: a second tab is a second copy of everything and shares only IndexedDB, which would need a lease written and refreshed while an import runs. (`import.ts`, `library.tsx`, `player.tsx`)
- **Audio is captured during the import, not streamed at playback.** One real host splices advertising per fetch — the same episode came back thirty seconds longer to a different client — so audio pulled next week would sit a whole ad break away from the timestamps made from it today. That is also why every byte goes through the proxy, which pins one User-Agent: a byte offset means nothing across two versions of a file. (`import.ts`, `worker/index.ts`)
- **The last position is parked in `localStorage`, not written to IndexedDB, when the page is closing.** A transaction opened at `pagehide` is not reliably committed, and there is no beacon for IndexedDB. `localStorage` is synchronous, which is the feature here. The store folds it back in on the next read — from both `getResource` and `listResources`, because a deep link to the player never touches the shelf. (`store.ts`, `player.tsx`)
- **A chunk that reached the end of the file is the last one.** Otherwise the seam rule drops its final segment as truncated and plans another chunk to re-transcribe the tail — paying twice and stitching the same words in again. Continuity checks do not notice, because the duplicate still lands on a consistent timeline. (`transcribe.ts`)
- **An uploaded episode is named with a file extension.** These endpoints read the audio format off the multipart filename and off nothing else: the same bytes are refused as `episode` — 400, `unsupported_audio_format` — and accepted as `episode.wav`, and also accepted _and correctly transcribed_ as `episode.mp3`, so the extension is a gate the decoder behind it never consults. It is derived from the type the store corrected rather than always sent as `.mp3`, because that would be the same lie `audioType` exists to stop telling. (`speech-to-text.ts`)
- **Both timestamp granularities are requested.** Asking for `word` alone comes back with `segments: null`, and segments are what place the seam between chunks. (`speech-to-text.ts`)
- **A transcription reply without a duration is refused.** That number is the byte-rate denominator the next chunk's seam is derived from; guessing it seams in the wrong place, silently. (`speech-to-text.ts`)
- **`words` is omitted, never `[]`.** An empty array reads as "word timing exists" and the player renders karaoke highlighting against nothing. (`transcribe.ts`, ADR 0004)
- **Translations are matched back by index, never by position.** A model that drops or reorders one entry would otherwise shift every later translation onto the wrong Line — invisible in the UI, wrong everywhere. (`annotate.ts`)
- **A translation block is marked asked before the request goes out, not after it comes back.** The player re-checks the window on every render, so a window whose request failed — or whose reply skipped a Line — would otherwise be sent again immediately, forever. A reload is what retries one. (`player.tsx`, ADR 0011)
- **A translation window is one request, and only two things send one: the screen opening, and playback resting for a second in a block the last window did not reach.** A window is the block being listened to and one either side, ten Lines to a block, and everything in it still missing goes out as a single span of at most thirty Lines — well inside one reply. It used to be forty Lines to a block, cut into batches sent four at a time, with the block behind sent the moment those landed and every refused request retried twice inside a second and a half, so opening an episode against a rate limit could send nine requests in a few seconds. Measured against a mock endpoint on the 828-Line fixture after the change, when a block was still twenty Lines — with ten, the two sizes below are 30 and 10, and a boundary comes twice as often: opening at 10:00 sent one request of 60 Lines; reopening the same place sent none; listening across a block boundary sent one of 20; dragging the progress bar 300 Lines sent one, not one per block crossed, which is what `SETTLE_MS` is for; pressing Back and reopening while a window was out sent nothing more, because the new screen waits on `windowsInFlight` and reads the answer back from the store; and a 429 was sent once, not retried, and followed by nothing until the next block. Never more than one in flight. A window that fails does not send the next one, since a rate limit is the provider asking for fewer requests. (`annotate.ts`'s `nextWindow`, `player.tsx`, `text-model.ts`, ADR 0011)
- **Whether an episode is Japanese is decided over the whole Transcript, never over the window being translated.** The studied language is usually unset and the answer then comes from kana in the text; a window that happens to contain none is not evidence, and Tokens appearing on some blocks and not their neighbours is the bug that follows. (`annotate.ts`, `player.tsx`)
- **Tokens are computed by the player, once per Transcript, and never by the Annotator.** kuromoji is local: no key, no request, nothing to wait for. Computing it inside `annotate()` made furigana ride on a translation's latency and made it unreachable for a reader who has a proxy and no Text Model. The effect that does it holds the same `busy` flag the translation effect does — one writer to the Transcript at a time, because both read the whole thing, merge into their copy and write it back — and its guard is the Lines themselves, so a Transcript that already carries Tokens loads no dictionary at all. (`player.tsx`, `pipeline.ts`'s `japaneseTokenizer`, ADR 0015)
- **A landed translation is written with `saveTranscript`, not `save`.** `save` also writes the Resource row, and the only Resource the player holds is the one it read when the screen opened — which would put back the `lastPositionSec` that has been written under it since. The two writers are live at the same time now that translation happens during playback, and landed Tokens are the third. (`store.ts`)

- **An import started from the player re-reads its Resource, and writes the position back afterwards.** The retry offered where the missing Lines are runs `store.save`, which puts the whole Resource row — including a `lastPositionSec` from whenever that screen opened. So it takes a fresh Resource going in, and calls `savePosition` again on the way out, because the import ran for minutes while something was almost certainly playing. (`player.tsx`)
- **A failed proxy response is reported with its body, and the body is scrubbed of `k=` first.** The Worker says which of three separately deployed things went wrong — `upstream answered 403` is somebody else's site refusing us, `host not on ALLOWED_HOSTS` is the proxy configured too narrowly, `bad or missing ?k` is a mistyped key — and reporting only the status turned all three into one unactionable number. That is not hypothetical: japanesepod101.com sits behind a CloudFront WAF that refuses Cloudflare's address range, so the feed reached the page as a bare "502" that read as a bug in this app. The scrub is in `proxyDetail` and not at each call site because it is the same rule as the message beside it, which names the feed rather than the proxy URL wrapping it: point `proxy.baseUrl` at something that is not this Worker and its error page may quote the request line back, key and all, into a message shown on screen and pasted into bug reports. (`proxy.ts`'s `proxyDetail`, `podcast-feed.ts`, `pipeline.ts`)
- **No secret leaves in an export.** `forExport` blanks them, and `backup.test.ts` sweeps the exported object for the values rather than checking three field names — because naming fields is exactly what failed when `proxy.key` joined Settings. (`backup.ts`)
- **The one export that does carry secrets is a different export.** Setting up a second device means retyping two base URLs, two keys, two model names and the proxy's URL and key, so `settings-transfer.ts` puts all of it in one string to copy — the exact opposite of the rule above, kept separate from it rather than folded into it. Its key is a constant in the bundle, which makes it obfuscation and not confidentiality: anyone who can load the page can decrypt any string it produces. That is a deliberate choice for one paste between a reader's own two devices. The export dialog used to say so on screen and no longer does — the copy there now explains what the string is for, not what it fails to protect against — so the file header is the only place that record lives. Anyone widening where this string is allowed to travel should read it first, and reach for the PBKDF2 passphrase it describes. (`settings-transfer.ts`, `settings.tsx`)
- **A pasted settings string is rebuilt field by field, never cast.** It is a trust boundary: a hand-edited one must not put a field of its own into IndexedDB, and a `nativeLanguage` this build has no strings for would leave the interface blank with no readable way back to the screen that could fix it. An unknown `targetLanguage` is dropped rather than refused, because absent is a real value there. (`settings-transfer.ts`)
- **Importing a settings string fills the form and writes nothing.** Save is still what keeps it, so a string pasted by mistake costs one Back rather than a Settings screen overwritten before anyone could look at it. The confirmation is looked up in the language that just arrived rather than through `t`, whose closure still answers in the language being left. (`settings.tsx`)
- **An import only ever adds.** A colliding id means the same Resource, and the copy already here may hold a playback position the file does not. (`backup.ts`)
- **Favorites are a store of their own, never a field of Settings, and they travel in the backup.** The Settings screen writes its row whole — from the copy it read when it opened, or from a pasted transfer string rebuilt field by field — so a list kept inside Settings would be emptied by the first Save after a paste. Their store is what database version 2 is, and the upgrade only creates a store that is missing: a version 1 Library opened by this build still had its episode on the shelf. In the backup they are an optional field and `BACKUP_VERSION` did not move, because an older build rebuilds the envelope from the fields it knows and so still restores a newer file's episodes, where a bump would have it refuse the file. An import adds only a show this browser has not starred, keeping the date it was starred here and with it its place. Which chip the home screen opens on is decided once, after both the settings and the favorites have been read, so a language's list is never drawn — and Apple never asked — on the way to the Favorites. (`store.ts`, `backup.ts`, `library.tsx`)
- **The connection check calls the endpoint the pipeline calls, in the mode it calls it.** A cheaper probe passes for a model that does not exist; an upload-only probe passes for a provider that cannot fetch a `url`, which is how every import moves audio. The transcription slot gets a real generated clip, and it is a quiet tone rather than digital silence because some endpoints reject an all-zero file as "no audio". (`model-check.ts`)
- **Furigana comes from kuromoji's `reading`, not `pronunciation`.** `pronunciation` writes long vowels as ー (ショーカイ); furigana is written しょうかい. (`japanese.ts`)
- **A Token that carries furigana is an inline-block, and that is a Safari workaround.** An inline box with `opacity` below 1 loses its ruby annotation in Safari 26, and a `pending` Token is exactly that. The readings then appeared only where the sweep had already been, because a Token drops back to opacity 1 on `now` — so a reader watched the furigana arrive one Token behind the audio instead of standing over the whole Line, and a click on the Line brought the rest of them back. Measured on one page in both engines: sixteen readings under `opacity: 0.55`, all sixteen drawn by Chrome and none by Safari, and `display: inline-block` the only change that restores them without costing something else. `isolation`, `will-change`, `translateZ` and removing the transition all leave them missing; fading the colour instead of the box does draw them, but `color` here overrides the part-of-speech colour it is supposed to be dimming. The selector is `:has(ruby)` and not every Token, because an inline-block cannot break across lines: over 7369 Tokens of real transcript the longest Token with a reading was six characters and the longest without was seventeen, an unsegmented run of kana that has no furigana to lose and every reason to keep wrapping on a phone. (`styles.css`)
- **Lighting a Line changes its colour and nothing else, so every Line of a Tokenised Transcript carries its Tokens, lit or not.** A reading takes room above its text, and drawn on the current Line alone it made that Line taller as it lit and shorter as it passed, moving every Line below it down and back up once a Line. Measured on ごん狐 at 375px, 57 of 65 Lines changed height as they lit: 6 to 30px in Chrome — and one by 67.5px, its inline-block Tokens wrapping onto an extra line where the plain text had not — and 9 to 58px in Safari 26.6. With every Line carrying them, 0 of 65 in Chrome. The other Lines' readings are `visibility: hidden` and their part-of-speech colour is `inherit`, so what shows is unchanged (ADR 0005) and what is laid out is the same in both states. A reading keeps its natural width, so one wider than its Token spaces the Token's text apart — 百姓 as 百 姓, even in a Line whose readings are hidden. A zero-width reading centred over its Token kept the text together and ran neighbouring readings into each other instead: over 仮釈放中 they overlapped, and a reading that cannot be read is worse than a gap. A Line swept by Word needs none of this: it is plain inline spans, which wrap exactly as its text does. Standard's 3% scale lift went for the same reason — it kept the layout still and slid the far end of a long Line nine pixels while it was being read. (`player.tsx`'s `LineText`, `styles.css`)
- **`Word` and `Token` are different things.** Word = audio timing from the ASR. Token = morphology from kuromoji. Japanese has no spaces, so their boundaries genuinely disagree; never merge the two arrays. Reconciling them for display is `tokenWords`' job, at render time (ADR 0005).
- **Tokens are swept by Word, never merged with them.** `tokenWords` matches both back onto `line.text` by character offset, so a Word covering three Tokens lights all three at once. (`shared/locate.ts`)
- **No class is named after a sweep state or a Line state.** `pending`, `now` and `said` are what `sweepState` puts on a Word or a Token, and `passed`, `current` and `next` are what the player puts on a Line, so a rule for any of those names written for something else lands on them too. The player's cover-and-title panel was called `.now` for an afternoon: on a phone, where that panel is hidden, it hid the Token being spoken. (`styles.css`, `shared/locate.ts`)
- **A Line's text carries its language, and so does its translation.** A Han character is drawn differently in Japanese and in Chinese, and the browser picks the form by the content's language — with the interface in Chinese, every kanji of a Japanese Transcript was set in its Chinese form. That is also why no font stack names a CJK family — one named there would override the choice — and why Station's Barlow is held to Latin by `unicode-range`. (`player.tsx`, `styles.css`)
- **A cover is loaded from its host, never proxied and never stored, and always with no referrer.** An offline Library, a cover moved upstream, and anything imported before covers were recorded show a monogram instead. Only http(s) URLs are taken from a feed, because the value becomes an `<img src>` (ADR 0017). (`podcast-feed.ts`, `cover.tsx`)
- **The Lines are memoised rows, and the callbacks they take are bound once.** A Word moving on re-renders the Line being spoken rather than all eight hundred. A callback created per render, or a prop that changes for every row at once — the whole revealed set rather than whether this row is in it — brings the old cost back without breaking anything visible. (`player.tsx`)
- **A Token is lit over a _range_ of Words, not on one of them.** The disagreement runs both ways, and the other direction is the common one for Japanese: an ASR returning one Word per kana — 917 of 1154 Words in a real Transcript were a single character — turns a five-character Token into five Words. Lighting it on the first and calling it said for the other four made the highlight strobe rather than sweep, worst on the furigana, which is small and dim. So `tokenWords` returns `[first, limit)` per Token and it runs until a _later_ Token claims a Word of its own; Tokens that share a first Word share the range and still light together, which an empty range would have broken. Measured in the browser over 23 seconds of a real episode: the highlight switched on and off 34 times before, 4 after — one per Line, before its first Word starts. (`shared/locate.ts`'s `tokenWords` and `sweepState`, `player.tsx`)
- **A Line's Words are sorted where they are assigned, not where they are read.** The endpoint's flat word list is not in time order: providers concatenate it segment by segment, segments overlap, and the midpoint rule then pulls a straddler back into the segment before it — 191 Words in one real Transcript started earlier than the Word printed in front of them. `locate`'s binary search cannot flicker on that (whatever index it returns only grows as `t` does), which is why nothing guards it downstream; what it does instead is quietly make a Word unreachable, so the fix belongs at the one place a Word becomes part of a Line. (`speech-to-text.ts`'s `toSegments`)
- **The studied language is optional; the native language never is.** Unset means the transcription call omits `language` and the translation prompt names no source language — both providers detect it — so one shelf can hold Japanese, Spanish and English episodes. Japanese Tokens are then decided by the transcript's own text (kana), which is why the Annotator takes the tokenizer as a thunk: only the Transcript knows whether that dictionary is worth loading. (`annotate.ts`)
- **kuromoji is behind a dynamic load and a thunk, and both halves matter.** A value import puts it in the main bundle for every reader; a static thunk downloads the dictionary for someone studying Spanish. The type it needs comes through an `import type`, which is erased before a bundler sees it. (`japanese.ts`, `pipeline.ts`)
- **There is no `confirm()` left, and the reason is stronger than the styling one.** A confirmation that blocks the page and reads as a browser error was the original complaint; what actually broke was that `confirm()` can answer `false` without showing anything — a sandboxed frame, or Chrome after a reader ticks "prevent this page from creating additional dialogs". The Settings back button then did nothing at all, forever, with nothing on screen to explain it, and since changing the Native Language is enough to make that form dirty, it was most of the ways off that screen. Both confirmations are two clicks on a button now, and focus leaving disarms. The shelf's Delete goes further, because the mis-operation it guards against is a double-click rather than a stray single one: arming replaces it with a _pair_, and the safe half is the one that inherits its position. Delete sits at the end of the row, so Cancel takes that slot — measured again once Delete became a bin icon: its centre at 1180px on a 1440px shelf, the armed pair spanning 1033–1200px, and `elementFromPoint` at that centre returning Cancel, which also holds focus — and Confirm appears to its left, on pixels nothing has clicked. Cancel also takes focus, so a reflexive Enter is the safe one too. The blur handler is on the pair rather than on each button, or moving between them would disarm and the two would be unreachable by keyboard. (`settings.tsx`, `library.tsx`)
- **A confirmation disarms on focus _moving_, never on focus going nowhere.** `relatedTarget` is null when a click focuses nothing, which is exactly what WebKit does with a click on a button — Chrome focuses one, so this was a Safari and iOS fault and nowhere else. Reading that as focus leaving unmounted Confirm between mousedown and mouseup, and the click then landed on whatever was underneath: the shelf asked for a confirmation and threw the answer away, every time, with the episode still on it. Measured with the focusout WebKit sends: the pair survives a null `relatedTarget` and the click deletes, a move to an element outside still disarms, and travel between Confirm and Cancel still does not. The cost is that clicking the page background now leaves a pair armed, and the next Delete, Cancel, Confirm or tab away is what closes it. (`library.tsx`)
- **The app's name is user-facing in three places and an identifier in four more, and only the first three may be edited.** Capitalising it means `index.html`'s `<title>`, the header brand, and the manifest's `name`/`short_name`. The other occurrences read the same and are not the name: `store.ts`'s `DB_NAME` addresses every reader's Library, `backup.ts`'s `BACKUP_FORMAT` is what a file someone exported last month is recognised by, `settings-transfer.ts`'s obfuscation secret decrypts strings already sitting in someone's notes, and the backup filename is matched by neither. Renaming any of those four silently orphans data that already exists. (`app.tsx`, `index.html`, `public/manifest.webmanifest`)
- **A modal locks every scroller behind it, and `main` is not the only one.** `showModal()` dims the page and makes it inert, and inertness is about clicks and focus — a scroll gesture still finds the nearest scroll box under the finger, and a scroller inside the dialog hands the rest of the gesture to whatever is behind once it reaches its own end. Both were reachable from the ask-AI popup: drag anywhere off the panel and the Lines moved behind it. The lock is one `body:has(dialog[open])` rule — from `body`, because Settings keeps its transfer dialogs in its top bar, outside `main` — naming the two scrollers this app has — `main`, which scrolls the shelf and Settings, and `.lyrics`, which scrolls the player where `main` does not. Naming the Lines separately is not belt-and-braces: they are the dialog's _sibling_, so nothing in the dialog chains into them and `overscroll-behavior` cannot reach them. That property still goes on the two boxes that scroll inside a dialog, for the iOS rubber-band the lock leaves behind. `overflow: hidden` keeps `scrollTop`, so a reader closing the popup is where they were — measured at 600px before, during and after. (`styles.css`)
- **The episode picker opens before the feed request, not after it.** A feed is fetched and parsed whole before there is a single episode to show, which is seconds on a show with a long archive — and a click on a recommendation used to leave the screen exactly as it was for all of them, with no sign it had been heard and nothing to press to take it back. The modal it was already going to open is the mask, so the wait costs no second overlay; `listEpisodes` takes an `AbortSignal` and the dialog's one button is Cancel while the request is in flight, because those bytes cross the reader's own proxy. Closing is what aborts, and an attempt that has been replaced or cancelled drops its reply rather than writing it over the list on screen. (`library.tsx`, `podcast-feed.ts`)
- **A key field is never `type="password"`.** That type paired with a submitting `<form>` is exactly the shape Safari and Chrome watch for to offer to remember a website password, for a field that has never held one — these are API keys, and on iOS the prompt greeted every reader who saved Settings and pressed Back. `SecretInput` masks with `-webkit-text-security` on a plain `type="text"` field instead, with autocomplete, autocorrect and autocapitalize all switched off so iOS does not also "help" by correcting or capitalising a key on entry. Below Firefox 126 there is no equivalent property and the key shows in the clear — accepted, since the CSS floor here is already Firefox 120 for `light-dark()`. (`settings.tsx`, `styles.css`)
- **Every text field is 16px on touch; 15px is the desktop's size and only the desktop's.** iOS Safari zooms the page in when it focuses a field computing under 16px, and does not zoom back out when the field is left — so one tap on the feed box left the whole app oversized until a reader pinched it back by hand. Every field inherited body's 15px, one pixel under the line. The floor goes on the base `input, select, textarea` rule under `(hover: none)` rather than on the two boxes that were reported, because the size that trips it is set once for all of them; the transfer dialogs' `.cipher` needs a second copy of the floor, being the one rule that is both more specific and later in the file. The other way out — `maximum-scale=1` on the viewport — buys the same thing by taking pinch-zoom away from everyone, on a page of small foreign-language text. Measured at 375px: no field under 16px anywhere, no horizontal overflow at 320px, and the six-row cipher box 160px tall instead of 100px, which is the whole of what the size bought. (`styles.css`)
- **`LANGUAGE_NAMES` is English because a prompt reads it, and it never labels the interface.** One table with two jobs is why the home screen's language chips sat in English in every interface: the same constant names the language to the Text Model, where a stable English name is the point, and named the buttons, where it is the bug. `languageName` writes the name in the reader's own language through `Intl.DisplayNames`, so eight more names in each of the eight tables never had to be written or kept in step. It asks by _script_ for the two Chinese codes — `of("zh-CN")` answers "中文（中国）" and `of("zh-TW")` "中文（台湾）", naming countries where this setting means Simplified against Traditional, while `zh-Hans`/`zh-Hant` answer "简体中文" and "繁体中文". The English answers match `LANGUAGE_NAMES` exactly, and a test holds them to it so the prompt and the English interface cannot drift apart. (`shared/i18n.ts`, `shared/model.ts`, `web/i18n.ts`'s `useLanguageName`)
- **The interface language _is_ the Native Language.** One setting, not two. It is cached in `localStorage` because Settings live in IndexedDB, which cannot be read before a first paint, and a shell that flashed English on every load is what someone who set their language is trying to avoid. The ask-AI prompt comes from the same table, asked in the native language, which is what makes the answer come back in it without a sentence instructing the model to. (`web/i18n.ts`, `player.tsx`)

- **That cache mirrors the _stored_ language, never the one a screen is showing.** Settings switches the interface the moment its dropdown changes, so you can see what you are picking — but nothing is saved until Save. Caching the preview left a reader who chose a language and walked away with an interface in one language and a Settings screen showing another, for good: the Back button's restore only runs if you press Back, and the read at boot could not correct a browser that had never saved anything. There are exactly two writers now, both facts about the store — a successful save, and the boot read, which _clears_ the cache when the store is empty. (`web/i18n.ts`, `app.tsx`, `settings.tsx`)
- **`completeStream` never retries, and nothing retries a rate limit.** `complete` and `completeJson` retry a server error or a dropped connection, half a second and a second apart. A rate limit is refused the same way that soon — a limit counted per minute does not reset in a second and a half — so retrying one only spent more of it, and a refused translation window went out three times on its way to failing. Streaming does not retry at all, because a retry after part of an answer has reached the ask-AI popup would show a second answer under the first. (`text-model.ts`)
- **An ask-AI answer renders no HTML, and `<br>` is the one tag turned into what it means.** react-markdown shows raw HTML as the text it was written in, and the answer is a model's, so that stays the rule — `rehype-raw` would put whatever the model writes into the page. But a Markdown table cell cannot hold a newline, so a model breaking a line inside one writes `<br>`, and tables came out full of it as literal text. `htmlBreaks` turns exactly that tag, spelled `<br>`, `<br/>`, `<br />` or `</br>` in any case, into a line break before the tree is rendered, and leaves a `<br>` inside code alone. `markdown.test.ts` renders through react-markdown itself and holds both halves. (`markdown.ts`, `player.tsx`)
- **The playback rate rides on `timeupdate`; only the highlight rides on `requestAnimationFrame`.** A hidden tab suspends rAF entirely while `<audio>` keeps playing — measured, not assumed: 0 frames in 5 seconds with playback advancing normally. Reading `audioRef` at save time is not the fix either: React detaches the ref before the unmount cleanup runs, which is what the `seconds` ref exists for. (`player.tsx`)
- **The playhead is written to the DOM, never to state.** The progress bar, its filled half (a custom property the track's gradient reads) and the two clocks beside it are set imperatively from the same frame that moves the highlight, because the alternative is a `setState` sixty times a second that re-renders every Line in the Transcript. The bar is left alone while a finger is on it, or the frame loop fights the drag. (`player.tsx`)
- **The follow-scroll puts the current Line back whenever the Lines above it reflow.** A translation window landing, Tokens arriving and a change of subtitle mode all change the height of Lines above the one being read. Safari has no scroll anchoring at all — `CSS.supports('overflow-anchor', 'auto')` is false in Safari 26.6 — so each of those pushed the Line being read down by everything that had just grown above it; and Chrome's anchoring holds still only what sits at the top of the list, so with every translation hidden at once the current Line still moved 113px on a phone. The follow effect is a layout effect that glides only to a _new_ Line and re-centres instantly on any other re-run, before the frame that would have shown the jump: 0px in Chrome afterwards, and within 1px in Safari. (`player.tsx`)
- **The service worker never touches `/kuromoji/`, and never anything cross-origin.** The dictionary is 17MB of gzip _content_, and a caching layer in front of it is the second way to reproduce the hour-long hang above. Cross-origin covers every model call, every proxy fetch and every episode download — none of it is the worker's to cache, and a range request is skipped outright so half a file is never stored as the file. (`public/sw.js`)
- **Apple's podcast charts are unreachable from a page and the search endpoint is the substitute.** `rss.marketingtools.apple.com` sends no CORS headers at all (measured: `TypeError: Failed to fetch`), while `itunes.apple.com/search` answers cross-origin with no key and hands back the `feedUrl` an import needs. Its `genreId` parameter is ignored — passing one still returns other genres — so the Language Learning filter is applied here, on `genreIds`, not there. (`itunes.ts`)
- **The recommendations reach the network twice a day and not once more.** A day-scoped `localStorage` cache holds the answer; only typing a search goes past it. An empty answer is deliberately not cached, or one bad afternoon blanks the section until midnight. (`itunes.ts`)
- **Playback is sampled with `requestAnimationFrame`, not `timeupdate`.** `timeupdate` fires about four times a second — visibly late for word-level highlight. The cost is contained by only setting state when `locate` returns a different Line or Word. (`player.tsx`)
- **Every colour is one `light-dark()` token, and no rule below the palette names a colour.** A hardcoded hex renders one screen wrong in one theme, for the half of users on the other one, which is the bug nobody reports. Cost: Chrome 123 / Safari 17.5 / Firefox 120, and on anything older every colour is invalid at once — a loud failure, not a subtle one. Each look's palette is written once under its own prefix (`--std-`, `--sta-`), and the names the rules use are aliases pointed at one of them, which is what lets the Settings previews draw a look that is not in force (ADR 0016).
- **The theme is the `data-theme` attribute and the look is `data-look`, and each default is its attribute's absence.** `index.html` applies both from localStorage in a blocking script before first paint, and `appearance.ts` applies a change the moment Settings makes it — a dark flash on every load, or a Standard page repainting itself as Station, is exactly what someone who chose otherwise is trying to avoid. Neither lives in Settings, and neither travels in the transfer string (ADR 0016). (`appearance.ts`, `index.html`, `styles.css`)
- **A faded Word is faded differently per theme.** `--pending` is the one token that is not a colour, so `light-dark()` cannot hold it and it states both themes the long way.
- **The proxy's key is its only gate, and it is a real secret because the page does not carry it.** An origin allowlist beside it would refuse nobody the key does not already refuse — `curl` omits `Origin` — while locking out a reader hosting the page themselves. (`worker/index.ts`, ADR 0009)
- **No TypeScript syntax that emits code.** Node runs these files by stripping types, so parameter properties, enums and namespaces break at runtime. `erasableSyntaxOnly` in tsconfig rejects them at typecheck.

## Testing conventions

- `node --test` with `node:assert`. No test framework, and don't add one.
- Test through a module's interface, not past it. Fakes are plain object literals or an injected `fetch`.
- **Use the real thing where a stub would lie.** `japanese.test.ts` loads the actual kuromoji dictionary. `speech-to-text.test.ts`'s fake endpoint reports the duration a byte range really represents and cuts segments on its own boundaries, because a fake returning segments aligned to the chunk edge would pass against arithmetic that is wrong.
- **There are no DOM tests**, deliberately — the logic worth testing is pure and lives below the components. IndexedDB and the browser half of kuromoji are driven in a real browser instead, with a throwaway page. That is not optional diligence: this refactor's last three bugs — a language table indexed by position, a placeholder still naming YouTube, and a dictionary hanging on a header — were all invisible to `tsc` and to 336 passing tests. The pattern held for the browser work that followed. A dialog rendering 576px wide inside a 375px viewport, a settings form overflowing at 320px, an interface stuck in a language the store had never been told about, and a Back button that did nothing because `confirm()` answered without showing itself: four real faults, none of which any amount of unit testing would have found, all of them one measurement away in a real browser.
- **The sweep cannot be measured in a hidden browser pane, and the way round it is `seeked`.** `requestAnimationFrame` is suspended there, so the frame loop that moves the highlight never runs — and `setTimeout` is clamped to a second, which makes a sampler taking one frame per second look like it is working. Seeking drives the same `sample()` the frame loop does, so stepping `currentTime` over a Line and reading the `.tok` class list after a few microtasks samples the real component deterministically, at about 2ms a frame.
- **A hidden pane never delivers a `<dialog>`'s `close` event**, so nothing that only happens in `onClose` can be measured there — verified on a bare dialog appended to the page, `showModal()` then `close()`, no event in three seconds. Whatever the close has to do belongs in a function the button also calls; `onClose` then covers Esc, and `close()` on a closed dialog raises nothing, so arriving both ways costs one no-op.
- A `ponytail:` comment marks a deliberate shortcut and names its ceiling. There are none left; the two that existed were a write mutex and a job queue, and both went with the server.

## Not yet done

- **No `LICENSE`.** Needs choosing before this is published anywhere.
- **No CI.** `npm test && npm run typecheck && npm run build` is the whole of it.
- **Nothing has been deployed, and no episode has been imported end to end** on the new architecture. Every piece is verified on its own and the two halves have never been run together against a real feed.
- **A Library is per-browser-per-origin.** A phone and a laptop are two Libraries with no path between them, and the two exports are the only bridges — the backup file for episodes, the transfer string for Settings. For a listening app the phone is a plausible primary device, so this is the sharpest open question (ADR 0008).
- **Translation can fall behind playback**, on a fast connection to a slow model: the Lines are there and the audio plays, the translations simply arrive under them late. Accepted (ADR 0011). A window that fails is not retried until the page is reloaded, and the only sign is the message beside the lyrics.
- **The ask-AI popup is one shot.** One fixed prompt about one Line, no input box, no history — so re-opening it asks the identical question. `completeStream(prompt: string)` takes a single string; follow-up means giving it a message list.
- **No retry for a `ready` Resource.** Re-importing would discard a Transcript that cost money, so redoing one is delete-and-import.
- **The iOS home-screen build has never been tried on a phone.** Installing is what exempts a Library from WebKit's seven-day storage cap, which is the whole reason the manifest exists — but standalone web apps on iOS have a long history of losing audio when minimised or when the screen locks. Play an episode, lock the phone, and find out before recommending it to anyone.
- **No Vite React plugin** — a dev edit reloads the page instead of hot-swapping the component, which loses playback position. Deliberate; production is unaffected.
