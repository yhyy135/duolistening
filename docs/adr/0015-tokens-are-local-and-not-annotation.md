# Japanese Tokens are local work, not part of annotation

Status: accepted.

The player computes a Transcript's Japanese Tokens itself, once, when it opens an episode with kana in it — independent of the translation window and independent of whether a Text Model is configured at all. `annotate()` no longer tokenizes anything, `AnnotatorOptions` no longer takes a tokenizer, and `pipeline.ts` exports `japaneseTokenizer` beside `buildAnnotator` instead of handing one to the other.

Tokens and translations were computed in the same call because they were introduced in the same step — the import pipeline of ADR 0005, which did everything to a Line at once. Nothing else ever joined them. Translation is a paid request to somebody's endpoint; a Token is kuromoji reading a dictionary in this browser, with no key, no network and no failure mode but its own. Bundling the two made the cheap half wait behind the slow half, so furigana and part-of-speech colouring appeared under a spinner's worth of latency for no reason — and made it unreachable entirely for a reader who has a proxy and no API key, which ADR 0012 went out of its way to make a supported way to use this app.

They also disagree about scope. ADR 0011 windows translation deliberately: it is billed per Line and an episode nobody finishes should not be paid for in full. A Token costs nothing per Line once the dictionary is in memory — the dictionary is the whole expense, and it is paid once — so windowing it bought nothing and cost the thing windowing is careful about elsewhere: Tokens appearing on some blocks and not their neighbours, depending on which windows a reader happened to reach.

The condition for loading the dictionary at all is unchanged, and it is still the reason it arrives as a thunk: `wantsJapanese` over the whole Transcript, never over a window, because a window with no kana in it is not evidence about the episode. `wantsJapanese` is all that is left of the Japanese question in `annotate.ts`, and the player is now the caller. kuromoji stays behind a dynamic import loaded as a classic script for the reasons already recorded — a shelf of Spanish must not download seventeen megabytes, and an ES module hands its gunzip dependency `undefined` where a script tag hands it `window`.

The Tokens are written back with `saveTranscript` rather than `save`, like a landed translation and for the same reason: `save` writes the Resource row too, and the only Resource the player holds is the one it read when the screen opened, under which a playback position has been written on every pause since. Both writers now take the same `busy` flag — one writer to the Transcript at a time — because each reads the whole thing, merges into its copy and writes it back, so two in flight would lose whichever landed first. Tokenizing takes it first, which delays a cold episode's first translation by the dictionary download. That is the right way round: the wait that was removed was on the free half.

We considered leaving Tokens unstored, since kuromoji is deterministic and re-running it costs milliseconds. Rejected: the dictionary is not milliseconds, and a stored Transcript that already carries Tokens is what lets a second visit load nothing at all — measured, zero requests under `/kuromoji/`.

This supersedes the part of [ADR 0011](0011-translate-while-listening.md) that says Tokens are computed for the Lines in a window when that window is annotated. They are computed for every Line, when the Transcript is opened. Nothing else in 0011 changes, and nothing else in [ADR 0005](0005-japanese-tagging-via-morphological-analyzer.md) does either: Tokens still come from kuromoji rather than the Text Model, they are still stored on the Line, and they are still shown only for the Line that is playing.
